# 🌱 기획 배경

출퇴근하기 바쁜 와중에도 오늘 왜 올랐는지, 왜 떨어졌는지는 항상 궁금했습니다. <br/>
그런데 막상 찾아보려면 뉴스, 커뮤니티, SNS를 따로따로 돌아다녀야 했고 <br/>
그렇게 모은 정보도 긍정 및 부정 의견이 뒤섞여 있어 결국 흐름을 파악하지 못한 채 포기하는 날이 더 많았습니다.

정보가 없는 게 아니라, 찾는 데 드는 시간과 수고가 너무 컸던 것입니다.

Hearsay는 그 불편함에서 시작됐습니다.

- 뉴스와 커뮤니티 게시글을 자동으로 수집하고
- 한국어 금융 특화 감성 분석 모델로 여론의 온도를 수치화하고
- "요즘 삼성전자 분위기 어때?" 같은 자연어 질문 하나로 바로 답을 얻을 수 있도록

정보를 모으는 시간을 줄이고, 판단에 더 집중할 수 있는 환경을 만드는 것이 목표입니다.

- 0 기준선 위는 긍정, 아래는 부정 여론이며 특정 시간대에 마우스를 올리면 점수를 확인할 수 있습니다.

### ④ 커뮤니티 Q&A

- "오늘 왜 올랐어?", "지금 분위기 어때?" 같은 자연어 질문에 커뮤니티, 뉴스 기반 답변을 반환합니다.
- 쿼리를 HyDE로 가상 문서화한 뒤 BM25 + 벡터 검색 결과를 RRF로 통합해 검색 품질을 높입니다. 뉴스 기반 팩트와 커뮤니티 여론을 구분해 답변합니다.
- 종목을 전환하면 이전 대화가 초기화되어 항상 선택된 종목 기준의 맥락으로 질문할 수 있습니다.

### ⑤ 게시글 피드

- 선택한 종목의 최신 커뮤니티, 뉴스 게시글을 우측 피드에서 확인할 수 있습니다.
- 각 게시글에는 KR-FinBERT가 분석한 감성 점수가 함께 표시됩니다.

# 🔬 개발 과정

## 감성 분석 모델 고도화: 키워드 매칭에서 파인튜닝까지

## 1. 왜 키워드 방식으로는 안 됐나?

Hearsay의 핵심 기능은 종목별 **매수/매도 여론 비율**입니다. <br>
이 값이 틀리면 서비스가 제공하는 모든 판단이 틀리기 때문에 감성 분석의 정확도가 곧 제품의 신뢰도입니다.

초기 구현은 긍정과 부정 키워드 리스트를 하드코딩하고 <br>
제목에 포함된 단어 개수를 세는 방식이었습니다.

구현이 단순하고 비용이 거의 들지 않는다는 장점이 있었지만, <br>
실사용 데이터에서는 **문맥을 이해하지 못한다**는 한계가 드러났습니다.

### 1-1. "문맥을 못 읽는다"는 게 무슨 뜻인가

#### 목적

게시글 제목에서 투자 감성을 추출해 $-1.0$(강한 부정) ~ $1.0$(강한 긍정) 사이의 점수로 변환하는 것이 목표였습니다.

#### 기술적 접근 방식

제목에 등장한 긍정 키워드 수와 부정 키워드 수를 세고 그 비율로 점수를 계산했습니다.

$$
score = \frac{n_{pos} - n_{neg}}{n_{pos} + n_{neg}}
$$

- $n_{pos}$ : 제목에 포함된 긍정 키워드 개수
- $n_{neg}$ : 제목에 포함된 부정 키워드 개수

```python
POSITIVE_KEYWORDS = ["상승", "급등", "매수", "반등", "호재", "가즈아", ...]
NEGATIVE_KEYWORDS = ["하락", "급락", "매도", "손절", "악재", "물렸", ...]

def compute_sentiment(title: str) -> float:
    pos = sum(1 for kw in POSITIVE_KEYWORDS if kw in title)
    neg = sum(1 for kw in NEGATIVE_KEYWORDS if kw in title)
    total = pos + neg
    if total == 0:
        return 0.0
    return round((pos - neg) / total, 2)
```
> 키워드가 하나도 없으면 분모가 0이 되므로,
> 감성 점수는 항상 중립(0.0)으로 처리됩니다.

<br>

#### 📉 실사용 데이터에서 드러난 한계

| 게시글 제목         | 실제 의미         | 감지된 키워드 | 판정   |
| -------------- | ------------- | ------- | ---- |
| "매도하지마 지금 존버해" | 긍정 (매수 유지 권유) | `매도`    | ✕ 부정 |
| "물타기 성공 ㅠㅠ"    | 긍정에 가까움       | `물타기`   | ✕ 부정 |
| "앤티들아"         | 부정 (안티 지칭)    | 없음      | ✕ 중립 |

핵심 문제는 세 가지였습니다.

**① 부정어를 처리할 수 없습니다.** <br>
"매도"라는 단어가 있을 때, 그것이 *"매도하라"*인지 *"매도하지 마라"*인지 구분할 방법이 없습니다. <br>
키워드 방식은 단어의 **존재 여부**만 보기 때문에 그 단어를 뒤집는 주변 표현을 볼 수 없습니다.

<br>

**② 사실상 3개 값밖에 나오지 않습니다.** <br>
수식은 연속적인 값을 계산하지만
짧은 제목에서는 대부분 한쪽 키워드만 등장합니다.

결과적으로 실제 출력은 -1, 0, 1 세 값에 집중되었습니다.

$$
n_{pos}=1,\ n_{neg}=0 \Rightarrow score = 1.0 \qquad
n_{pos}=0,\ n_{neg}=1 \Rightarrow score = -1.0
$$

⮕ 살짝 긍정과 확신에 찬 긍정이 똑같이 $1.0$이 됩니다. <br>
여론 **비율**을 계산하는 서비스에서 강도 구분이 사라지면 소수의 극단적인 글이 전체 지표를 흔듭니다.

<br>

**③ 커뮤니티 표현을 사람이 따라가야 합니다.** <br>
"ㄱㄱ", "가즈아", "존버", "앤티" 같은 표현은 계속 새로 생깁니다. <br>
그때마다 리스트를 수동으로 갱신해야 했고 <br>
반영되기 전까지는 해당 게시글이 모두 중립(0.0)으로 분류되었습니다.

<br>

> [!IMPORTANT]
>
> **문제는 키워드의 개수가 아니라 <판단 단위>였습니다.**
>
> 키워드 방식은 **단어**를 기준으로 판단합니다. <br>
> 하지만 감성은 **문장 전체의 문맥**에서 결정됩니다.
>
> 따라서 키워드 리스트를 계속 늘리는 대신, <br>
> **문장 자체를 이해하는 모델**이 필요했습니다.

<br>

## 1-2. 그래서 어떤 모델을 골랐나

#### 목적

문장 전체를 문맥으로 이해하는 모델이 필요하다는 것은 분명했습니다. <br>
다만 모델 선택은 **정확도만의 문제가 아니라, 운영 구조와 함께 판단해야 하는 문제**였습니다.

Hearsay가 모델에 요구한 조건은 다음 세 가지였습니다.

| 조건 | 이유 |
| --- | --- |
| 문맥 이해 | 1-1에서 확인한 부정어/강도 문제 해결 |
| 상시 추론 가능 | 10분 주기 크롤링으로 추론이 지속적으로 발생 |
| 한국어 + 금융 도메인 | 종목, 수급, 실적 관련 표현이 대부분 |

이 중 **상시 추론 가능 여부**가 모델 선택을 결정했습니다.

#### 기술적 접근 방식

후보 모델을 다음 기준으로 비교했습니다.

| 방법 | 문맥 이해 | 추론 비용 | 한국어 금융 | 비고 |
| --- | --- | --- | --- | --- |
| 키워드 카운팅 (기존) | 낮음 | 없음 | - | 문맥 처리 불가 |
| GPT API | 높음 | 건당 과금 | 높음 | 운영 비용 증가 |
| KoELECTRA (범용) | 중간 | 무료 | 보통 | 금융 특화 아님 |
| **KR-FinBert-SC** | 높음 | 무료 | 높음 | 금융 사전학습, 로컬 추론 |

#### 운영 비용을 고려한 모델 선택

정확도만 보면 GPT API가 가장 좋은 선택입니다. 하지만 Hearsay에서는 **비용이 한 번 발생하고 끝나는 구조가 아니었습니다.**

```python
# main.py — 크롤링이 10분마다 무기한 반복된다
_scheduler.add_job(crawl_all, "interval", minutes=settings.crawl_interval_minutes)
```

크롤링 주기가 10분이므로 **하루 144회**, 매 사이클마다 5개 종목의 신규 게시글이 유입됩니다. <br>
즉 추론 대상은 고정된 데이터셋이 아니라 **시간에 따라 계속 증가하는 스트림**입니다.

| 구분 | 1회성 작업 | Hearsay의 감성 분석 |
| --- | --- | --- |
| 처리 대상 | 정해진 N건 | 지속적으로 유입되는 스트림 |
| 비용 성격 | 총비용 확정 | 운영 기간에 비례해 누적 |
| 종료 시점 | 있음 | 없음 |

건당 과금 방식은 **종료 시점이 없는 작업**에 적용되는 순간 비용을 예측하기 어려워집니다. <br>
서비스를 오래 운영할수록 분석 대상 종목이 늘어날수록 비용도 선형적으로 증가합니다.

반면 로컬 모델은 **한 번 배포하면 추론 횟수와 무관하게 비용이 고정**됩니다. <br>
따라서 먼저 **로컬 추론이 가능한 모델**을 후보로 제한한 뒤 그 안에서 가장 높은 정확도를 기대할 수 있는 모델을 선택했습니다.

> [!NOTE]
>
> **GPT는 사용하지 않았나요?**
>
> 사용했습니다. 다만 **역할이 다릅니다.**
>
> GPT는 상시 추론이 아니라 **한 번만 수행하면 되는 작업**, 즉 학습 데이터 라벨링에 활용했습니다. <br>
> 종료 시점이 있는 작업이므로 총비용을 예측할 수 있기 때문입니다.

<br>

#### 왜 KR-FinBert-SC였나

`snunlp/KR-FinBert-SC`는 **금융 텍스트로 사전학습된 한국어 BERT**입니다. <br>
로컬 추론이 가능해 운영 비용 조건을 만족하면서도 범용 한국어 모델(KoELECTRA 등)보다 "수급", "물량", "실적 컨센서스"와 같은 금융 도메인 표현을 더 잘 처리할 것으로 판단했습니다.

#### 도입하면서 정한 설계

**① 확률 3개를 하나의 연속 점수로 변환**

모델은 `positive` / `neutral` / `negative` 세 라벨의 확률을 반환합니다. 이를 다음과 같이 하나의 점수로 변환했습니다.

$$
score =
\begin{cases}
0.0 & \text{if } P(neutral) \geq 0.5 \\[6pt]
P(positive) - P(negative) & \text{otherwise}
\end{cases}
$$

```python
def _score_from_probs(probs: dict[str, float]) -> float:
    if probs.get("neutral", 0.0) >= settings.sentiment_neutral_dominance:
        return 0.0
    return round(probs.get("positive", 0.0) - probs.get("negative", 0.0), 3)
```

확률의 차이를 사용하기 때문에 결과는 **-1.0 ~ 1.0** 사이의 연속적인 점수가 됩니다. <br>
이를 통해 1-1에서 언급한 "3개의 확률값만 존재하는 문제"를 해결했습니다.

또한 `P(neutral)`이 0.5 이상이면 점수를 0으로 고정했습니다. <br>
모델이 중립이라고 판단한 글에서 미세한 확률 차이까지 점수에 반영되면 의미 없는 값이 누적될 수 있기 때문입니다.

<br>

**② 모델은 프로세스당 한 번만 로드**

모델 크기가 약 400MB이므로 요청마다 로드할 수 없습니다. <br>
싱글톤으로 한 번만 생성하고 서버 시작 시점(`lifespan`)에 미리 로드해 첫 번째 크롤링이 모델 초기화를 기다리지 않도록 했습니다.

<br>

**③ 배치 추론과 중복 연산 방지**

신규 게시글을 32건씩 배치로 추론하고 대상은 `sentiment_score`가 `NULL`인 게시글로 한정했습니다. <br>
이미 분석이 끝난 게시글은 다시 추론하지 않으므로, 크롤링이 반복되더라도 추론량은 **신규 유입 게시글 수에만 비례**합니다.


> [!IMPORTANT]
>
> **하지만 한계도 있었습니다.**
>
> KR-FinBert-SC는 금융 **뉴스 기사**를 중심으로 학습된 모델입니다.
>
> 따라서 "3분기 영업이익이 컨센서스를 상회했다"와 같은 뉴스체 문장은 잘 처리하지만, <br>
> "앤티들아", "존버 가즈아"처럼 종목 토론방에서 사용하는 커뮤니티 문체는 학습 분포 밖에 있습니다.
>
> 즉 **금융 도메인에는 적합했지만 커뮤니티 문체에는 적합하지 않았습니다.**
>
> 이 한계를 해결하기 위해 다음 단계에서는 실제 종목 토론방 데이터를 활용한 파인튜닝을 진행했습니다.
